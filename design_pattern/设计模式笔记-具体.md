# 简单工厂模式

不直接给客户端暴露对象创建的实现细节，而实通过一个工厂类来负责创建产品类的实例。

包含3个角色(类)，以payment为例

1. 工厂角色： PaymentFactory
2. 抽象产品角色 : Payment
3. 具体产品角色 : Alipay,WechatPay

```Python
class PaymentFactory:
    def create_payment(self, method):
        if method == 'alipay':
            return Alipay()
        elif method == 'wechat':
            return WechatPay()
        else：
        	raise TypeError("no such method")
            
#client
paymentFactory = PaymentFactory()
pm = paymentFactory.create_payment('alipay')
```

这样做的好处是在客户端，**程序只需要关注用户传进来的支付方式，而一些内置的需要传的参数 可以在工厂中基于条件预设完成，例如采用花呗支付，则返回use_huabei =True的alipay对象**，减轻客户端需要传参数量。且方便拓展，只需要写好具体产品角色，然后再工厂中加入该方法即可，而具体产品角色又是对抽象产品角色的实现。

违反了**职责单一**原则 一个工厂可以创建多种逻辑，也违反了**开闭原则**，新具体产品角色需要修改工厂类代码



# 工厂方法模式

定义一个用于创建对象的接口（工厂接口），让子类决定实例化哪个产品类

包含4个角色(类)，以payment为例

1. 具体工厂角色：AlipayFactory、WechatPayFactory
2. 抽象产品角色 : Payment
3. 具体产品角色 : Alipay,WechatPay
4. （新增）抽象工厂角色:PaymentFactory

```python
class Payment(ABC):
    @abstractmethod
    def pay(self,money):
        ...
     
class WechatPay(Payment):
    def pay(self, money):
        return f"wechat pay{money}"
    
class Alipay(Payment):
    def pay(self, money):
        return f"Alipay pay{money}"

class PaymentFactory(ABC):
    @abstractmethod
    def create_payment(self):
        ...
class AlipayFactory(PaymentFactory):
    def create_payment(self):
		return Alipay()
```

 优点，每个具体产品都对应某个具体工厂类，不需要修改抽象工厂类代码，对客户端隐藏实现细节

缺点，每增加一个具体产品类，新增一个具体工厂类，代码太多了



# 抽象工厂模式

内容：定义一个工厂类接口，让工厂子类来创建一系列相关或互相依赖的对象

eg: 一部手机需要手机壳、CPU、操作系统三类对象进行组装，每类对象都有不同的种类。对于每个具体工厂，分别生产一部手机所需的三个对象。

相比于工厂方法模式，抽象工厂模式中每个具体工厂都生成一套产品。

包含4个角色(类)，以造手机为例



1. 具体工厂角色：MiFactory、HuaweiFactory、IPhoneFactory
2. 抽象产品角色 : PhoneShell、CPU、OS
3. 具体产品角色 : BigShell、SmallShell、AppleShell、SnapDragonCPU、MediaTekCPU、AppleCPU、Android、IOS
4. 抽象工厂角色: PhoneFactory
5. 客户端 负责弄成一个手机

该工厂模式可以限制一套产品只能用哪些东西

```python
#客户端上：
class Phone:
	def __init__(self, shell:PhoneShell, cpu:CPU, os:OS):
		self.cpu =cpu
		self.shell = shell
		self.os = os
	def show_info(self):
	print(f"phone information {self.cpu.show_cpu()},{self.shell.show_shell},{self.os.show_os}")

def make_phone(factory:PhoneFactory):
    cpu = factory.make_cpu() 
    os = factory.make_os()
    shell = factory.make_shell()
    return phone(cpu= cpu, os = os, shell = shell)

p1 = make_phone(MiFactory())
p1.show_info()
```

利于产品一致性，将客户端与类的具体实现相分离，每个工厂造一个完整的产品系列

缺点是难以支持新种类（抽象）产品，得重新写工厂 甚至写抽象工厂

# 单例模式

保证一个类出来的实例只有一个，并提供它的全局访问点

角色：单例（singleTon）

优点：对唯一实例的受控访问，单例相当于全局变量，但防止了命名空间被污染

值得注意的是 在实例初始化时  必先调用父类对象（如果没有重写 就是object的__new__方法返回一个空的实例对象），单例模式通过把这个new出来的实例给存在类属性里了，每次初始化如果它存在 那就返回这个在进行初始化，所以始终只有一个。

```python
class Singleton:
    def __new__(cls, *args, **kwargs):
        if not hasattr(cls, "_instance"):
            cls._instance = super().__new__(cls)
        return cls._instance

class MyClass(Singleton):
    def __init__(self, a):
        self.a = a

a = MyClass(10)
b = MyClass(20)
print(a.a, b.a) #20 20
print(id(a),id(b)) #相同地址
```

**应用于一个类只需要一个实例的情况，如日记类，数据库类等**

python里的单例模式，通常用类变量来实现，如果这个类变量存在 则返回该实例，否则初始化

# 策略模式

将一组可互换的算法（策略）进行封装，使它们彼此独立，并且可以在运行时自由切换，而不影响使用算法的客户端代码。

角色:

Context 上下文

AbstractStrategy 抽象策略

ConcreteStrategy 策略

同一业务流程存在**多种算法/规则**

算法之间**频繁切换**

使用 `if-elif-else` 导致代码**臃肿、不可维护**

新增算法需要**修改已有逻辑（违反 OCP）**

策略模式的目标是：

- **消除条件分支**
- **实现算法与使用者解耦**
- **对新增策略开放、对修改关闭**

```python
#两种经典写法 一种是字典注册+context转换解耦 一种是抽象基类强约束 + context解耦
from abc import ABC, abstractmethod

class Strategy(ABC):
    @abstractmethod
    def execute(self, data):
        ...
class StrategyA(Strategy):
    def execute(self, data):
        return data * 2

class StrategyB(Strategy):
    def execute(self, data):
        return data ** 2
class Context:
    def __init__(self, strategy: Strategy):
        self.strategy = strategy

    def set_strategy(self, strategy: Strategy):
        self.strategy = strategy

    def run(self, data):
        return self.strategy.execute(data)
    
________________________________________

def l1(x):
    return abs(x)

def l2(x):
    return x ** 2

STRATEGIES = {
    "L1": l1,
    "L2": l2
}

class Context:
    def __init__(self, strategy_name):
        self.strategy = STRATEGIES[strategy_name]

    def run(self, x):
        return self.strategy(x)
```

- 只有 **1–2 个固定分支**
- 算法不会变化
- 性能极端敏感（多态有微小开销）

此时简单函数即可，**不要为了模式而模式**。



# 模板模式

锁死流程，释放细节

模板方法模式的本质不是“继承”，而是：
 固定算法结构，延迟变化点。

模板方法本身也会被子类继承，但它“不该、也通常不会被子类重写”，因此流程是固定的

```python
class Template(ABC):
    """Don't override run function"""
    def __run(self):
        self.step1()
        if self.use_step2():
            self.step2()
        self.step3()
	@abstractmethod
    def step1(self): ...
    @abstractmethod
    def step2(self): ...
    @abstractmethod
    def step3(self): ...
    
    def use_step2(self):
        return true
        
class TemplateA(Template):
    def step1(self):
        pass
    def step2(self):
        pass
    def step3(self):
        pass
    def use_step2(self):
        return False
```

# 装饰器模式

core:在**不修改原有对象**结构的前提下，**动态地**为对象**添加功能**

反模式就是用继承去堆功能 有个Base类 实现了某种方法，其他类去继承它 新增功能。

类爆炸

组合困难

功能顺序不可控

 **继承在“横向功能扩展”时是失效的**

而装饰器模式的解法：

核心对象
→ 加日志
→ 再加缓存
→ 再加权限

**每一层都是“包一层”**，而不是“改一层”。

**角色**：

原始接口：Component

被装饰对象： ConcreteComponent

抽象装饰器：Decorator

具体装饰器：ConcreteDecorator

```python
#类装饰器
class Component:
    def operation(self): ...

class Decorator(Component):
    def __init__(self, component):
        self.component = component

    def operation(self):
        return self.component.operation()

class LogDecorator(Decorator):
    def operation(self):
        print("log")
        return self.component.operation()
    
eg：
class Service:
    def run(self):
        print("run")
class LogDecorator:
    def __init__(self, service):
        self.service = service

    def run(self):
        print("log")
        return self.service.run()        
s = LogDecorator(Service())
s.run() #log/nrun
#多层装饰
s = CacheDecorator(LogDecorator(Service()))
```

不适合用装饰器模式：需要改变**核心算法逻辑** 需要控制整体流程（那是模板） 功能之间强耦合

装饰器模式通过对象组合而非继承的方式实现功能扩展，使系统在保持接口一致性的同时具备良好的灵活性与可扩展性。

装饰器的叠加不是运行期的“嵌套调用”，而是定义期完成的“**函数重绑定**”。
