# 面向对象设计SOLID原则

1. 开放封闭原则：一个软件实体如类、模块和函数应该对扩展开放，对修改被关闭。即软件实体应在尽量不修改原有代码的情况下进行拓展
2. 里氏替换原则：所有引用父类的地方必须能透明地使用其子类的对象，支持传父类参数进来的函数或对象，必然要支持子类传进来能用。
3. 依赖倒置原则：高层模块不应该依赖底层模块，二者都应该依赖其抽象（接口）;抽象不应依赖细节（只规定要实现什么）；细节应该依赖抽象（细节是对抽象的实现，所以抽象有什么就要做什么）。换言之，要针对接口编程，而不是针对实现编程。
4. 接口隔离原则：使用多个专门的接口，而不使用单一的总接口，即客户端不应依赖那些它不需要的接口。简单而言，一个animal基类你又要会飞 会游泳 会跑（接口） 不现实 因为子类动物都要继承他 不一定每个都会，然而你细分责任的话 设三个陆生动物、水生动物、天上动物，那子类就可以不需要依赖一些没用的接口。
5. 单一职责原则：不要存在多于一个导致类变更的原因。通俗的说，即一个类只负责一项职责。你支付就支付，别整上什么其他功能。

# 设计模式分类：

**3大类**

1. 创建型模式：**工厂方法模式、抽象工厂模式、创建者模式、单例模式**、原型模式
2. 结构型模式：适配器模式、桥型模式、组合模式、装饰模式、外观模式、享元模式、代理模式
3. 行为型模式：解释器模式、责任链模式、命令模式、迭代器模式、中介者模式、备忘录模式、观察者模式、状态模式、**策略模式**、访问者模式、模板方法模式

创建型模式关注在怎样创建对象，隐藏底层实现

结构型模式关注在几个类之间，怎么协同工作在一起

行为型模式关注类的行为

# 设计模式

设计原则：

简单接口，深度功能

- [ ] 以urllib为例，这东西发个post请求要关注很多底层细节，不如request库一根，简单调用request.post就可以直接完成

依赖抽象，而非具体

- [ ] 以OrderService这个类为例，本来包含了EmailSender这个类，业务要新增微信等其他消息通知功能，此时，应该用一个抽象类把Sender抽象出来，方便拓展，其他sender都继承这个抽象sender，而不是写死EmailSender，这样你就要去改OrderService的代码

高内聚，低耦合

# 工厂模式

有一个数据库类，包含connect方法以及连接用户端口的属性初始化

还有一个函数，会调用这个数据库类创建几个数据库连接，返回连接状态

以上代码有几个问题

- [ ] 硬编码连接参数，难以维护
- [ ] 代码重复，每次创建连接都要输入相同参数

```python3
#此时可以用工厂函数,参数较少，建造较为方便，作为一个类工厂

def connection_factory(db_type):
	#用模块的话,从config.py里引
	from xx import db_config
	#函数内置连接信息
	db_config = {
		"main":{
			"host":"...",
			"port":"3306",
			"username": "root",
			"password":"..."
		},
        "analyse":{
			"host":"...",
			"port":"3306",
			"username": "root",
			"password":"..."
		},
        "design":{
			"host":"...",
			"port":"3306",
			"username": "root",
			"password":"..."
		}
	}
	
	if db_type in db_config:
		return DatabaseConnection(**db_config[db_type])
	
```

这样的话有新的连接可以直接加入db_config，省去麻烦，如果为了保证信息安全，也可也在配置文件里面弄，一个db_config，用dotenv引入就行，getenv，然后用os去获取。

或者直接单开一个.py文件，但这样上传的时候就有点操蛋，不如直接用.env

# 单例模式

**应用于一个类只需要一个实例的情况，如日记类，数据库类等**

python里的单例模式，通常用类变量来实现，如果这个类变量存在 则返回该实例，否则初始化

```
class DatabaseConnection:
	_instance = None
	
	def __new__(cls, *args, **kwargs):
```

# 策略模式

同样的一件事，用不同策略去做，将每个策略包装成一个类

这时就要有个抽象基类 abc

**规范接口**

```
from abc import ABC, abstractmethod

#除了用这个约束外 还可以用protocol约束
#抽象基类不可以被初始化 里面的抽象方法其子类必须实现
class ProcessStrategy(ABC):
	@abstractmethod
	def process_file(self, filepath)
		pass

class CsvProcessStrategy(ProcessStrategy):
	def process_file(self, filepath):
		print('Processing csv file')
class TxtProcessStrategy(ProcessStrategy):
	def process_file(self, filepath):
		print('Processing txt file')
class FileProcessor:
	def__init_(self, file_path):
	self.file_path = file_pathself.file_type = file_path.split('.')[-1]
	def process_file(self):
		if self.file_type == 'xlsx':
   			ExcelProcessStrategy().process_file(self.file_path)
   		elif self.file_type == 'csv':
    		CsvProcessStrategy().process_file(self.file_path)
    	elif self.file_type == 'txt':
    		TxtProcessStrategy().process_file(self.file_path)

```

其实就是子类继承总的父类，然后在文件处理类调用不同的策略类，用抽象基类来规范接口，方便拓展
